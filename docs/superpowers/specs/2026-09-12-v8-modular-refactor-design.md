# AStockQuant v8.0 模块化重构设计

日期：2026-09-12  
状态：设计已在对话中逐节确认，等待用户审阅本书面规格  
基线：AStockQuant v7.6.3

## 1. 背景

AStockQuant 已连续迭代多个版本，现有功能能够覆盖行情、周线策略、单股与组合回测、严格 300 验证、牛熊双引擎、世坤因子、尾盘两日策略和本地模拟，但工程结构已经妨碍继续可靠开发。

当前主要问题：

- `main.py` 约 3163 行，同时包含网络请求、数据处理、策略、回测、后台线程和九个界面页面。
- `tail_strategy.py` 约 983 行，同时包含筛选、行情源、缓存、撮合和审计。
- 数据文件、运行状态、报告和程序文件混在安装目录中，升级需要人工判断哪些文件不能覆盖。
- 同类功能散落在多个页面，用户需要记忆正确的操作顺序。
- 网络故障、数据不完整和任务恢复由各页面分别处理，产生重复修复。
- 工作区通过复制完整目录保存版本，形成大量版本副本，难以确认唯一源码。

v8.0 是一次结构重构，不是策略优化。相同冻结数据和相同参数必须产生与 v7.6.3 等价的策略信号、成交、费用和资金曲线。

## 2. 目标

1. 建立单一、可维护的 Python 工程，停止复制完整源码目录发布修复。
2. 把界面、应用服务、策略、回测、数据源、缓存、模拟券商和报告分开。
3. 保留 v7.6.3 的全部策略、数据、页面能力和审计能力。
4. 把九个并列入口收敛为五个按工作流程组织的中心。
5. 将程序与个人数据分离，升级程序时不再覆盖个人数据。
6. 统一行情源切换、任务进度、断点恢复、错误表达和日志。
7. 建立统一券商接口和模拟券商，但 v8.0 不连接真实账户、不发送真实订单。
8. 使用冻结数据建立回归基准，任何关键差异都阻止交付。

## 3. 非目标

- 不修改周线规则 1、2、3、世坤因子或尾盘两日策略的交易含义。
- 不利用已有前向结果重新选择参数或因子权重。
- 不重新下载已经存在且校验通过的历史数据。
- 不在 v8.0 接入国泰海通、MiniQMT 或其他真实券商账户。
- 不把 vn.py、RQAlpha、easytrader 或其他项目整体复制进工程。
- 不在重构阶段改变费用、滑点、T+1、涨跌停或无法成交规则。
- 不承诺策略收益。

## 4. GitHub 架构依据

v8.0 只借鉴成熟项目的边界设计，不复制其具体实现：

- [vn.py](https://github.com/vnpy/vnpy)：事件引擎、主引擎、应用模块、交易网关和界面分离。
- [RQAlpha](https://github.com/ricequant/rqalpha)：数据源、券商、模拟撮合、账户和交易费用通过清晰接口协作。
- [easytrader](https://github.com/shidenggui/easytrader)：券商适配器独立于策略研究和用户界面。

采用“模块化单体”而不是直接以 vn.py 为底座重写。原因是当前软件已有大量 A 股特定的冻结验证、缓存和审计行为，整体替换底座会显著扩大迁移风险；机械拆文件又无法消除职责耦合。

## 5. 总体架构

依赖方向固定如下：

```text
ui -> services -> core
              -> strategies
              -> backtest
              -> data interfaces -> data adapters
              -> broker interface -> paper broker
              -> reports
```

规则：

- `core` 不依赖 PySide6、requests、AKShare 或具体文件格式。
- `strategies` 不导入界面类，不直接请求网络，不直接读写文件。
- `backtest` 只接收标准行情、策略信号、费用配置和账户状态。
- `ui` 只发起应用命令、显示状态和渲染结果，不包含选股公式或撮合逻辑。
- `services` 负责组织完整用例，不重复实现策略或数据规则。
- `data adapters` 和 `broker adapters` 实现接口，可以独立替换。
- 模块之间只传递明确的数据模型，不传递任意字典作为长期公共接口。

## 7. 统一核心模型与接口

核心模型使用带类型的数据类表达：

- `Instrument`：代码、名称、市场、板块、上市状态。
- `Bar`：代码、时间、开高低收、成交量、成交额、来源。
- `QuoteSnapshot`：实时价格、涨跌幅、振幅、换手率、流通市值和时间。
- `Signal`：策略编号、代码、时间、方向、强度、原因和参数版本。
- `Order`：订单编号、账户、代码、方向、数量、限价、状态和时间。
- `Trade`：订单编号、成交价格、数量、费用、滑点和成交原因。
- `Position`、`AccountSnapshot`：持仓、现金、权益、峰值和风险状态。
- `RunManifest`：运行编号、程序版本、策略版本、参数、样本哈希、数据截止日、数据哈希和错误摘要。

主要接口：

- `MarketDataProvider`：获取股票池、实时快照、日线和分钟线。
- `MarketRepository`：读取、合并、校验和原子保存行情。
- `Strategy`：从标准输入生成信号，不负责成交。
- `BacktestEngine`：按标准行情、信号和费用规则生成订单、成交及账户曲线。
- `Broker`：查询账户、提交订单、撤单和接收状态回报。
- `RunStore`：保存运行清单、明细、曲线、错误和报告。
- `TaskService`：启动、暂停、恢复、取消和报告进度。

v8.0 只提供 `PaperBroker` 的可用实现。`MiniQmtBroker` 仅保留接口占位，并固定为禁用状态。

## 8. 策略迁移

必须迁移并保留：

1. 原始周线趋势、离场、风险和资金规则。
2. 入场规则 1 推荐、规则 2 严格、规则 3 折中。
3. 世坤六因子候选排序及四种入场对照。
4. 单股历史回测、批量独立回测和共享资金组合。
5. 严格 300 样本闸门、数据质量审计和运行清单。
6. 牛熊双引擎及指数仓位 0%、10%、20%、30%、40% 对照。
7. 尾盘两日策略的 13 项过滤、14:50 候选、14:55—14:56 入场、T+1/T+2、移动止盈、止损、到期、无法成交顺延和分钟冲突保守路径。
8. 自选股、模拟账户和历史报告查看能力。

策略函数必须保持因果性，只能读取当时及之前的数据。重构不允许顺便调参。

## 9. 五中心界面

左侧只保留五个一级入口：

| 入口 | 职责 | 迁入的旧能力 |
|---|---|---|
| 首页 | 数据状态、最近扫描、最近回测、风险提示和继续任务 | 行情概览与各页面进度 |
| 数据中心 | 股票池、K线、日线/分钟缓存、数据质量、增量更新和 CSV 导入 | 行情与K线、研究样本、数据准备、尾盘数据管理 |
| 策略中心 | 查看策略规则与版本、配置扫描、运行候选筛选 | 策略说明、周线策略、世坤因子、尾盘今日筛选 |
| 回测验证 | 单股、批量、共享资金、严格300、牛熊双引擎和尾盘分钟回测 | 四个分散回测页面与验证页面 |
| 模拟交易 | 候选池、模拟订单、持仓、成交和统一风控 | 模拟账户与风险控制 |

每个中心内部使用页签。首页只显示状态与下一步操作，不堆放全部参数；高级参数留在具体任务的配置页签。界面统一展示任务状态：未开始、运行中、已暂停、失败、不完整、已完成。

## 11. v7.6.3 数据迁移

首启迁移步骤固定为：

1. 检测旧安装目录及下列已知文件。
2. 生成只读清单，记录大小、日期范围和 SHA-256。
3. 将原文件复制到新数据目录的临时位置。
4. 校验复制后的大小、哈希、股票数量和关键日期范围。
5. 原子切换到正式目录并写入 `data_manifest.json`。
6. 生成用户可读的迁移报告。

兼容对象：

- `cache/`
- `tail_strategy_cache/`
- `research_sample.json`
- `validation_snapshot_v1.json.gz`
- `research_data_checkpoint.json`
- `watchlist.json`
- `paper_account.json`
- `tail_strategy_state.json`

迁移规则：

- 永远复制，不移动，不删除旧文件。
- 首次迁移不批量改变原始 CSV、JSON 或压缩快照格式。
- v8 通过 `legacy_v7.py` 读取旧格式，并在正常增量写入时逐步使用新仓库路径。
- 同一数据集重复迁移必须幂等，不产生重复记录。
- 任一步失败都撤销未完成的新目录，旧版保持可运行。
- 损坏文件移入新数据目录的隔离区并记录，不修改旧文件。
- 日线近似结果不得混入分钟精确回测。

## 12. 运行与报告组织

每次扫描、数据准备、回测或验证都获得唯一 `run_id`。一个运行目录必须包含：

- `manifest.json`
- 参数快照
- 数据与样本哈希
- 候选、订单、成交、持仓和费用明细
- 每日资金账本与完整曲线
- 指标和年度结果
- 数据缺口与错误清单
- 运行日志引用

运行未通过完整性闸门时，状态只能是“不完整”或“失败”，不得生成看似成功的结论。导出核实包由 `RunStore` 中的同一份数据生成，不重新计算策略。

## 13. 行情容错

`DataService` 维护数据源优先级和健康状态，页面不感知具体提供方。每个请求记录提供方、请求时间、数据时间、记录数和错误。

数据状态：

- `healthy`：主源成功且完整性校验通过。
- `degraded`：备用源成功，或存在不影响本次任务的已知缺口。
- `offline`：没有来源能够提供满足契约的数据。
- `incomplete`：取得数据但数量、字段或时间范围不满足任务要求。

强制闸门：

- 全市场接口不得把单页 100 只误认为完整市场。
- 严格 300 必须在输入、合格样本、本地加载、信号帧和质量审计阶段全部为 300。
- 所需字段缺失的股票不能悄悄使用零值。
- 实时行情与历史行情必须记录各自的数据时间。
- 免费分钟数据覆盖不足时，只报告实际精确覆盖率。

重试使用有上限的退避和熔断，避免快速重复请求。备用源切换由数据服务统一完成。

## 14. 任务与错误处理

下载、扫描、回测、迁移和报告统一使用 `TaskService`。任务保存：编号、类型、阶段、完成量、总量、断点、开始时间、更新时间、状态和最后错误。

错误分为：

- 网络错误
- 数据不完整
- 数据损坏
- 配置错误
- 策略输入错误
- 撮合约束错误
- 迁移错误
- 内部程序错误

用户提示固定包含“任务阶段、股票或数据范围、来源、原因、下一步操作”。详细 traceback 只写日志。一个股票失败时是否继续由任务契约决定；严格 300 等完整性任务必须终止，允许部分覆盖的研究任务可以继续但必须标记不完整。

文件写入全部采用临时文件、刷新、校验和原子替换。运行目录完成后写入完成标记；没有完成标记的目录不能被界面当作成功结果打开。

## 15. 模拟券商与未来扩展

`PaperBroker` 实现统一订单状态机：新建、已提交、部分成交、全部成交、已撤销、拒绝和失效。它执行 A 股 100 股整数手、T+1、涨跌停、停牌、现金、费用和无法成交规则。

策略只产生信号；应用服务把信号转成订单；券商产生订单回报和成交。回测与模拟共用订单、成交、费用和账户模型，但使用不同时间驱动器。

v8.0 的真实交易能力固定关闭：

- 不读取券商账号或密码。
- 不安装 `xtquant`。
- 不创建真实交易会话。
- 不提供可点击的真实下单开关。

以后确认国泰海通账户开通官方接口后，可以在新的独立设计中实现 `MiniQmtBroker`，不修改策略和界面核心。

## 16. 测试策略

### 16.1 单元测试

分别覆盖核心模型、数据归一化、质量检查、每项策略规则、撮合、费用、账户、缓存、迁移和报告。

### 16.2 接口契约测试

每个行情提供方必须返回相同标准字段和单位。每个券商实现必须通过相同订单状态、现金、持仓和错误契约。

### 16.3 集成测试

覆盖从读取冻结数据到产生信号、成交、资金曲线、运行清单和核实包的完整流程；覆盖任务暂停、重启和继续。

### 16.4 v7.6.3 黄金回归

从 v7.6.3 保存冻结输入和期望输出。相同输入与参数下：

- 股票代码、信号日、买入日、卖出日、方向和退出原因必须逐项一致。
- 交易数量和顺序必须一致。
- 100 股取整、手续费、印花税和滑点规则必须一致。
- 货币值允许的绝对误差不超过 0.01 元；非货币浮点指标使用明确的小数容差。
- 严格 300 各阶段数量必须为 300。
- 四种入场方案和五档指数方案必须全部保留。
- 尾盘 13 项过滤和分钟成交边界必须保持一致。

任何非预期差异都阻止交付。若确认旧版存在缺陷，修复必须另立需求、单独测试和单独版本，不能混入纯重构差异。

### 16.5 迁移与破坏性测试

使用旧数据副本测试正常迁移、重复迁移、空间不足、损坏文件、中断恢复和回滚。测试必须证明旧数据没有被删除或修改。

### 16.6 界面与交付测试

- 五个工作中心可以构造和切换。
- 长任务不阻塞界面。
- 失败、不完整和成功状态显示不同。
- Windows 安装包可从全新目录安装和启动。
- 从最终 ZIP 解压后重新运行全部自动测试。
- ZIP 不包含账户、缓存、状态、样本或历史运行数据。

## 17. 版本管理

v8 开始只维护一个 Git 工程：

- 开发分支保存未发布改动。
- 发布使用语义化标签，如 `v8.0.0`、`v8.0.1`。
- 修复版本不复制完整源码目录。
- `CHANGELOG.md` 只记录用户可见变化、迁移影响和验证结果。
- `dist/` 保存构建产物，不作为源码真相。
- v7.6.3 作为独立只读回退包保存，不放进 v8 源码树。

当前工作区没有 Git 元数据。不得为了保存本设计而把包含大量旧版本的现有目录整体初始化为仓库。v8 实施的第一阶段将创建干净的单一仓库，并把本规格作为首批受控文档提交。

## 18. 分阶段实施

### 阶段 1：干净工程与兼容层

建立单一工程、核心模型、配置、数据目录解析、旧数据只读清单、迁移与回滚。此阶段不迁移策略界面。

### 阶段 2：数据、策略和回测核心

按黄金回归顺序迁移数据提供方、周线策略、世坤因子、组合回测、严格 300、牛熊双引擎和尾盘策略。每迁移一个模块立即与 v7.6.3 对照。

### 阶段 3：应用服务与五中心界面

接入统一任务服务、运行存储和五中心页面。旧功能全部完成映射后才移除临时兼容入口。

### 阶段 4：模拟券商、交付与回退验证

接入 `PaperBroker`、执行全量回归、迁移演练、Windows 安装包复验和隐私检查。保留 v7.6.3 回退包。

每阶段都必须可以独立测试。阶段失败不得影响 v7.6.3。

## 19. 交付验收

v8.0 只有同时满足以下条件才能交付：

1. 五个工作中心包含全部旧功能。
2. `main`/启动模块只负责装配和启动，不包含策略、行情或回测实现。
3. 核心和策略层不依赖 PySide6 或具体网络库。
4. v7.6.3 黄金回归全部通过。
5. 旧数据迁移可验证、可重复、可回滚，且不删除旧数据。
6. 网络失败不会让界面崩溃，数据不完整不会被标成成功。
7. 所有运行有统一 `run_id`、参数、数据哈希、完整曲线和错误清单。
8. 真实券商交易保持关闭。
9. 最终 ZIP 独立解压测试通过且不含个人数据。
10. v7.6.3 回退包仍可独立使用。

## 20. 已确认决策

- 重构范围：代码和界面全面整理。
- 技术路线：模块化单体，不整体替换为 vn.py。
- 界面主线：研究验证优先。
- 一级入口：首页、数据中心、策略中心、回测验证、模拟交易。
- 交易层：建立统一接口，v8.0 仅启用模拟券商。
- 数据位置：`%LOCALAPPDATA%\AStockQuant`。
- 迁移方式：复制、校验、原子切换、可回滚，不删除旧数据。
- 策略要求：纯重构保持 v7.6.3 行为，修复缺陷另行立项。
- 版本方式：单一 Git 工程和标签发布，不再复制源码目录。
